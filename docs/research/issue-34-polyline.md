# Issue #34: связанные контуры wireframe-фигур

Исследование базы и реализация от 2026-09-22. Разделы исследования фиксируют состояние до изменений. Актуальный контракт: [Shape strokes](../spec/render/architecture.md#shape-strokes); результаты реализации приведены в конце.

## Уточнённый вывод после просмотра Shapes

Пользователь уточнил цель: устранить рваные стыки существующих толстых линий и проверить, не слишком ли дорог текущий способ. Приоритет — геометрическая непрерывность; сокращение instances не является самостоятельным критерием успеха.

Рекомендация для фиксированных wire-фигур: явно связанные контуры, расширяемые в треугольники с корректными miter joins и настоящим bevel при превышении miter limit. Качество задаёт алгоритм стыков. Статический шаблон со смежностью — способ не пересобирать известный контур на CPU каждый кадр; он сам по себе не исправляет стыки. Существующий 44-байтный instance пригоден для повторяющихся фигур. Производительность нового пути пока не измерена.

Найдено два соответствующих демо: `examples/spinning_cube` (название сайта **Spinning Shapes**) и `examples/bench_shapes` (**Shape Renderer Bench**). Для первого собран и исполнен временный стенд на основе его настоящего `main.c`: вызваны собственные `draw_room()` и `draw_shape()`, сняты все четыре фигуры через `nt_gfx_read_pixels`. Кадры 800×600 лежат в `build/issue34/spinning-shape-0.png` … `spinning-shape-3.png`, скрипт — `build/issue34/capture_demo.py`. Вращение фиксировано для воспроизведения; управление мышью и браузерная версия не проверялись. Каждый кадр показал 3 draws суммарно для комнаты, заполненной фигуры и общего батча линий. Это ещё раз опровергает предположение о draw на каждый сегмент.

В демо есть также куб, у которого в вершине сходятся три ребра: это граф, а не обычная ломаная. Нельзя произвольно выбрать двум из трёх рёбер miter и считать узел решённым. Для таких узлов отдельно сравнить аккуратные окончания/округлённое покрытие; кольца и меридианы имеют определённую смежность. В bench_shapes есть ещё линии сетки и буквы, построенные независимыми вызовами `line`: не соединять их скрытым поиском совпадающих координат.

### Мировая и экранная толщина

Оба режима оправданы и могут использовать одни контуры/instances. Различается расширение в shader:

- **WORLD**: ширина в единицах мира, как сейчас; подходящий выбор для геометрии в сцене.
- **SCREEN**: ширина в явно выбранных экранных единицах; удобна для debug-контуров, которые должны читаться при зуме. Не смешивать CSS pixels и framebuffer pixels: связать ширину с фактическим viewport и его масштабом.

По итогам обсуждения пользователь согласовал два явных режима и реализацию связанных контуров («ок, делаем»). Старое значение `set_line_width(0.02)` должно сохранить смысл. Режим можно задавать для батча вместе с толщиной; смена режима должна завершать накопленные линии. Не требуется прибавлять поле режима каждому instance. Screen-space путь требует отдельной корректной обработки near plane до perspective divide. В реализации экранный setter принимает толщину и размеры активного viewport; отдельного режима на каждом instance нет.

Практика других движков:

| Движок / renderer | Контракт |
|---|---|
| [Unity Line Renderer](https://docs.unity3d.com/6000.0/Documentation/Manual/line-rendering-introduction.html) | Строит полигоны с шириной в мировых единицах |
| [Three.js LineMaterial](https://threejs.org/docs/pages/LineMaterial.html) | Явно поддерживает CSS-pixel width и world-unit width через `worldUnits` |
| [Babylon.js GreasedLine](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/core/src/Materials/GreasedLine/greasedLineMaterialInterfaces.ts) | Разделяет поведение ширины параметром `sizeAttenuation`, также имеет `resolution` |

Другой подход к видимым стыкам — круглые окончания каждого толстого отрезка с перекрытием, используемые, например, в [Three.js LineMaterial shader](https://github.com/mrdoob/three.js/blob/dev/examples/jsm/lines/LineMaterial.js). Он может быть компактным решением для непрозрачных debug-линий и сохранять segment batching. Это иной внешний вид, без точных miter/bevel; пересечения, depth и AA требуют проверки, а корректную прозрачность перекрывающихся сегментов он не гарантирует. Для явно связанных контуров я предпочитаю описать реальные joins и не маскировать их произвольным удлинением прямоугольников.

Сглаживание границ — отдельная проверка качества после исправления стыков. Текущий shader выдаёт сплошной цвет; в WebGL-инициализации демо `antialias` не включён. На native `nt_gfx_desc_t.antialias` сейчас не настраивает уже созданный GLFW context. Поэтому «включить MSAA одной галкой везде» нельзя считать проверенным решением; AA не заполняет геометрические щели. У круга всего 16 сегментов: исправленные стыки сохранят его гранёность. Дополнительная детализация и AA не должны скрыто превращать #34 в полный редизайн renderer.

Фраза задачи «circle becomes 1 draw call instead of 16 line instances» сравнивает разные величины. Сейчас круг уже требует один draw call при неизменном состоянии и свободном буфере.

- `nt_shape_line_instance_t`, строка 87: два конца и RGBA8 занимают 28 байт.
- `emit_wire_edge`, строка 636: пишет отрезок в общий массив; переполнение вызывает flush.
- `nt_shape_renderer_flush`, строка 897: весь массив линий отправляется одним `nt_gfx_draw_indexed_instanced(0, 6, 4, line_count)`.
- `nt_shape_renderer_circle_wire`, строка 1060: 16 отрезков.
- `nt_shape_renderer_sphere_wire`, строка 1172: три отдельных больших круга, 48 отрезков.

## Важные существующие свойства

1. Толщина задаётся в мировых единицах: смещение вычисляется до умножения на `u_vp`. Она не является постоянной толщиной в пикселях. Для сравнения готовых алгоритмов это принципиально.
2. Линии ориентируются к `u_cam_pos`. Матрица VP сама по себе не задаёт направление ортографической камеры для такого billboard-алгоритма. Не обещать исправление всех ортографических видов без отдельного контракта камеры.
3. Pipeline линий не включает alpha blending. Альфа в цвете сама по себе не означает поддержанную полупрозрачность. Устранение щелей не даёт автоматически корректный прозрачный stroke на пересечениях.
4. Есть depth и overlay, переключения состояния с flush, кольцевое размещение instance-данных, потеря и восстановление контекста. Новый путь обязан сохранить эти свойства.
5. Капсула уже ограничивает `body_half = max((height - 2*radius)/2, 0)`. При нулевой длине тела совпадают два экватора и вырождаются четыре осевых сегмента. Это достижимый вход, который нужно учитывать.
6. `mesh_wire` перебирает рёбра треугольников. У произвольной сетки нет единственного очевидного порядка polyline; поиск смежности и удаление дублей не относятся к этой задаче.
7. Спецификация описывает общие классы renderer, но не фиксирует полный контракт shape-линий; `architecture.md` даже упоминает debug-line как будущий renderer. Толщина, стыки, концы и вырождения здесь установлены по коду, а не выданы за уже утверждённый текст спецификации.

## Сравнение подходов

| Подход | Польза | Цена и ограничения | Оценка |
|---|---|---|---|
| Расширить instance отрезка соседями `prev/a/b/next` | Можно сохранить общий батч смешанных фигур; исправить стыки в shader | Минимальный payload становится 52 B вместо 28 B на сегмент, без учёта метаданных стыка; подготовка всех точек на CPU остаётся. Bevel требует дополнительной геометрии | Разумный вариант, если важнее единый батч и нужны динамические ломаные |
| Статические шаблоны контуров и instance целой фигуры | CPU передаёт transform и цвет один раз на фигуру; смежность неизменна; соответствует существующему instancing заполненных фигур | Нужны частный layout шаблона, shader и ограниченное staging. Разные шаблоны разделяют draws; обработка острых проекций обязательна | Предпочтительный кандидат для четырёх фиксированных фигур из #34 |
| CPU tessellation связанных линий | Проще пошагово проверять геометрию; можно использовать обычные треугольники | Камерозависимые вершины пересчитываются и загружаются каждый кадр; больше данных, возможны отличия depth/order при использовании текущего CPU-batch | Полезен как эталон для проверки, слабее как основной путь повторяющихся фигур |
| Нативный `GL_LINE_STRIP` / `GL_LINE_LOOP` | Простая геометрия | Не даёт переносимый контракт толстой линии со стыками; нынешний gfx рисует треугольники. Потребуется расширить backend ради неподходящего примитива | Отклонить |

Рекомендация: исследовать и реализовать частные шаблоны фиксированных wire-фигур внутри существующего `nt_shape_renderer`, если нужен выигрыш в подготовке и объёме данных. Публичный универсальный polyline API из этой задачи не следует. Если приоритет — только исправить щели при минимуме новых ресурсов и сохранении одного смешанного draw, вариант со смежными отрезками нужно оставить полноценной альтернативой. Выбор между этими двумя путями должен опираться на реальные сцены; число instances само по себе не метрика скорости.

## Предлагаемое устройство шаблонов

```text
Init / restore:
  известные локальные контуры → смежность prev/current/next + роли вершин
                            → immutable VBO/IBO через существующий nt_gfx

Каждый вызов *_wire[_rot]:
  center + scale/shape parameters + quaternion + RGBA8 → фиксированный staging

Flush:
  upload instances → draw по шаблону
  shader: локальные точки → параметры фигуры → rotation + translation
         → world-space направления к камере → расширение + стыки
         → существующий depth bias → VP → аппаратный clipping
```

**Новый instance-формат не обязателен.** Уже есть `nt_shape_instance_t` размером 44 B: center[3], scale[3], rot[4], RGBA8. Для капсулы существующий filled-path уже использует radius/body_half и метку полусферы в шаблоне. Эти же параметры позволяют деформировать соседние точки wire-шаблона. Не вводить mat4 на фигуру, пользовательские handles или новый asset type.

Топология должна описывать реальные контуры:

- Круг: один замкнутый контур из 16 точек.
- Сфера: три замкнутых контура в одном шаблоне; их пересечения не становятся joins.
- Цилиндр: два кольца и четыре самостоятельных отрезка в одном шаблоне. Концы стоек не соединять последовательно с кольцами.
- Капсула: меридианы и экваторы; противоположные меридианы можно объединить в два замкнутых профиля без изменения набора рёбер. Экваторы остаются отдельными контурами. Нулевое тело требует убрать дублирующее кольцо и нулевые сегменты; повторное использование sphere-шаблона возможно после проверки ориентации и набора рёбер.

Шаблон — индексированные треугольники, не обязательный GPU triangle strip. Все несвязанные контуры одной фигуры могут лежать в одном VBO/IBO и рисоваться одним instanced draw.

Генерация нескольких фиксированных шаблонов один раз в init согласуется с текущим `build_templates()`. Это не импорт контента и не тяжёлый runtime builder. Не нужен новый формат pack или обязательная сборка debug-геометрии отдельным инструментом. При необходимости полностью убрать init-вычисления возможны статические массивы, но это отдельный обмен размера бинарника на время init.

## Честная стоимость варианта с шаблонами

Динамический payload на фигуру теоретически уменьшается до 44 B: круг 448→44, сфера 1344→44, цилиндр 1008→44, капсула 1904→44. Это расчёт layout, не результат benchmark новой реализации. Число вершин и работа shader не исчезают; вычисление стыков добавляет ALU, а bevel добавляет треугольники.

Один круг остаётся одним draw. Четыре разных wire-фигуры могут стать четырьмя draws вместо текущего одного. Однотипные фигуры батчатся вместе до лимита и границ состояния. Нельзя реализовать «один draw на вызов *_wire»: это уничтожит текущий батчинг.

Нельзя механически расширять существующее `inst_data[type][2048]` без оценки памяти. Четыре новых типа по 2048 instances × 44 B добавят **360448 B (352 KiB) CPU staging**, ещё до шаблонов. Текущий GPU instance buffer теоретически можно переиспользовать через существующий ring cursor; отдельный динамический GPU-буфер не является обязательным. Размер и организацию ограниченного CPU staging следует выбрать по ожидаемому числу debug-фигур и показать в diff явно. Новый общий allocator или универсальная command queue ради этого не оправданы.

Layout укладывается в имеющийся gfx: например, три vec3 позиции и роль/сторона занимают четыре атрибута; четыре атрибута instance дают восемь всего. Capsule tags могут быть w-компонентами трёх vec4. Нужно проверить конкретный окончательный layout: максимум 16 attribute locations, максимум 8 instance attributes, stride ≤255 B, корректное выравнивание. Небольшие фиксированные шаблоны допускают uint16 indices; увеличение числа instances не увеличивает индекс шаблона.

## Что означает корректный join

Для вершины P, соседей A/B и камеры C берутся входящий/исходящий отрезки в world space, затем нормали к ним относительно направления C−P. У двух соседних сегментов должны совпадать вычисленные граничные вершины стыка. На обычном повороте miter получается из нормализованной суммы нормалей с поправкой на угол; простое усреднение без поправки меняет толщину.

Обязательные особенности:

- Miter limit: ограничивать длинный выступ и переходить на **настоящий bevel**. Clamp длины в формуле miter не создаёт bevel и может сузить контур.
- Bevel требует ролей входящей/исходящей границы и заполняющей треугольной геометрии. Шаблон только из двух вершин на точку недостаточен для полноценного переключения топологии.
- Замыкание использует модульную смежность, без отдельного видимого шва.
- Независимые отрезки сохраняют butt endpoints; никаких автоматических соединений по совпадению координат.
- Нулевая длина, почти 180° в проекции, направление вдоль луча зрения и камера в вершине не должны давать NaN/Inf. Геометрическая вырожденность при движении камеры — обычный случай, а не повод для assert. Нужны определённые конечные fallback/split правила.
- Положения и join math использовать с `highp` в GLES shader; текущий `mediump` не является основанием повторять его для более чувствительной геометрии.
- Сохранять мировую толщину. Не делить на clip.w ради удобства и не вводить скрытую зависимость от viewport/DPR. Расширение в world space позволяет аппаратно отсечь полученные треугольники, но не заменяет обработку вырожденных направлений.
- Если будет выбран экранный алгоритм, это отдельное изменение контракта: viewport, perspective divide и near-plane clipping до вычисления экранных направлений. Смена единиц толщины не входит в исправление стыков.
- Самопересечения и пересечения независимых колец не являются стыками одной ломаной. Глобальное устранение overdraw и корректная полупрозрачность требуют другого масштаба решения.

## План реализации и приёмки

1. В спецификации render зафиксировать границы shape renderer: мировую толщину, виды контуров, caps/joins, предел miter, достижимые вырождения, depth/overlay и ограничения прозрачности. Добавить модуль в карту spec/index; не выдавать новый текст за старый контракт.
2. Сделать изолированный прототип круга с соседями и bevel на существующих gfx API. Это самый рискованный шаг. Проверить под острым углом, при пересечении near plane и при смене направления взгляда. Прототип предлагаемого shader в этом исследовании не выполнен.
3. Сравнить две основные альтернативы на малой смешанной сцене и большой сцене одного типа: CPU emit/flush, uploaded bytes, draws, GPU time, статическая RAM, WASM и gzip-размер. Без этих измерений не обещать ускорение.
4. После выбора пути перенести фиксированные фигуры, сохранив обычные line/mesh_wire. Не расширять public API и backend без доказанной необходимости; если она появится, применить правило AGENTS «No ceremony» и согласовать с разработчиком.
5. Проверить реальные пиксели, а не только счётчики: стыки/шов, широкая линия, острые проекции, near plane, нулевое тело капсулы; asymmetric center/rotation и разные radius/height. Сохранить видимые рёбра при depth и overlay.
6. Существующим fake backend проверить batching, state flush при смене VP/camera/width/depth, отсутствие старых uniform values, capacity overflow и ring wrap. При отдельной очереди wire-фигур `set_line_width` должен учитывать её: сейчас он смотрит только на `line_count`.
7. Проверить context loss/restore, включая неудачное восстановление; ресурсы новых шаблонов должны жить по существующему контракту. Не добавлять test hooks в production ради новой реализации — текущих fake trace и readback достаточно.
8. Native и WebGL2 pixel checks, затем штатные проверки из docs/build.md. Mobile-GPU, shader quality и performance остаются unverified до этих запусков.

`test_shape`: 37/37, native ring tests: 2/2. Исследовательский GL capture: 1/1; fake trace дал приведённые выше значения. При readback драйвер выдал `Pixel-path performance warning: Pixel transfer is synchronized with 3D rendering.` Это предупреждение синхронного чтения пикселей, не ошибка изображения и не измерение производительности renderer.

`reproduce.py` компилирует отдельные временные translation units с флагами свежей compilation database и линкует их с библиотеками этого же ворктри. Производственные исходники не подменяются. ## Первичные внешние источники

- [Cesium: Robust Polyline Rendering with WebGL](https://cesium.com/blog/2013/04/22/robust-polyline-rendering-with-webgl/) — пример triangle-based thick lines с соседями; отдельный разбор near-plane проблем экранного расширения. Его географическую точность и дополнительные режимы не нужно переносить в Neotolis.
- [Three.js: LineMaterial](https://threejs.org/docs/pages/LineMaterial.html) — мировые и экранные единицы толщины представлены разными режимами; это полезное различие контрактов, не предложение зависимости.
- [WebGL 2.0 specification](https://registry.khronos.org/webgl/specs/latest/2.0/) — границы целевого API; реализацию сверять с существующей валидацией vertex layouts в `engine/graphics/nt_gfx.c`.

Предлагаемых сторонних библиотек нет.

## Реализованный результат

Добавлены `nt_shape_renderer_polyline` и `nt_shape_renderer_set_line_width_pixels`.
Старый `set_line_width` сохраняет мировые единицы и переключает обратно из pixel mode.
Прямоугольник и треугольник используют связанные контуры; circle/sphere/cylinder/capsule — постоянные GPU-шаблоны с соседними точками. Куб и mesh wire остаются графом независимых рёбер.

Отдельная линия сохраняет 28 B upload и два треугольника. Polyline хранит 52 B на сегмент в очереди на 1024 сегмента. Miter ограничен четырьмя половинами толщины, затем используются bevel-треугольники. Screen-space путь отсекает near plane до деления на w. Кривую семплирует вызывающий код.

Измерения на свежих библиотеках (`build/issue34/final-probes.log`):

| Случай | Upload базы | Upload реализации | Draws база → реализация |
|---|---:|---:|---:|
| Круг | 448 B | 44 B | 1 → 1 |
| Сфера | 1344 B | 44 B | 1 → 1 |
| Цилиндр | 1008 B | 44 B | 1 → 1 |
| Капсула | 1904 B | 44 B | 1 → 1 |
| Все четыре типа вместе | 4704 B | 176 B | 1 → 4 |
| 512 кругов | 229376 B | 22528 B | 1 → 1 |
| 513 кругов | 229824 B | 22572 B | 2 → 2 |

Это измерение объёма и draw calls, не FPS и не GPU timing. Смешанные типы требуют разных draws; штатное Spinning Shapes теперь выдаёт 4 draws для сферы/цилиндра/капсулы вместо 3, куб сохраняет 3. CPU больше не генерирует и не вращает каждый отрезок четырёх фиксированных фигур. Очереди независимых линий, polyline и фиксированных wire-шаблонов взаимоисключающие и используют один staging union: это убрало 143360 B дублирующей статической памяти, а максимум CPU staging остался равен старой очереди линий. Цена на GPU: постоянные шаблоны около 86.6 KiB и streaming buffer polyline 52 KiB; один shader/program, две pipeline и пять vertex inputs сверх базы. Накладные расходы driver objects не измерены.

Аппаратный WebGL 2 замер в Chromium 153 через ANGLE/D3D11 на Intel UHD Graphics: 15 прогревочных и 45 измеренных кадров, pixel width 1.25. Пустой кадр занимал 0.479 ms GPU. 10k отдельных линий дали 0.2 ms CPU median, 0.4 ms p95, 0.649 ms GPU и 2 draws. 10k wire-тел, сгруппированных вызывающим кодом по типу, дали 0.3/0.6 ms CPU, 3.249 ms GPU и 28 draws; вместе с 10k линий — 0.4/0.7 ms CPU, 3.449 ms GPU и 30 draws. Те же тела в произвольном чередовании дали 27.1/33.3 ms CPU и 7500 draws; с чередующимися линиями — 64.5/80.5 ms CPU и 20000 draws. Узкое место — смена wire-очереди, а не число объектов. Поэтому renderer сохраняет порядок, а владелец массового debug-списка группирует непрозрачные depth-tested команды до вызовов API; `bench_shapes` показывает именно этот режим.

Новый круг: `build/issue34/circle-fixed.png`; исходный: `build/issue34/circle-baseline.png`.
Реальные кадры демо: `build/issue34/spinning-fixed-0.png` … `spinning-fixed-3.png`; исходные — `spinning-shape-0.png` … `spinning-shape-3.png`.
Щели на внешних стыках устранены. Гранёность 16-сегментного круга и отсутствие AA сохраняются.

Native GL и WebGL 2 прошли одинаковые восемь пиксельных проверок: внешний стык через auto-flush и butt end, замкнутый шов, bevel на остром угле, pixel width на разных глубинах, отдельный viewport, near-plane crossing, восстановление настроек и кольцевые записи буфера. WebGL-стенд собран из того же файла тестов против свежих wasm-debug библиотек; GLFW setup удалён из временного TU, размер очереди для старого ring test подставлен как 2048, производственные исходники не подменялись. Сборка — `python build/issue34/build_web_probe.py`, запуск — `build/issue34/stroke_web_probe.html` через локальный HTTP server. Результат: `8 Tests 0 Failures`; console ошибок/предупреждений нет. В браузере также просмотрены wire-режимы сферы, цилиндра и капсулы в штатном demo.

`bash scripts/format_and_check.sh` проходит после восстановления LFS ресурсов. Документ и build-стенды не добавляют зависимости в runtime.
